## Intent

**Problem:** Set-aside import rows currently require manual data entry to correct, lacking AI interpretation (`row_interpret` purpose) to automatically propose structured transaction fixes with privacy safeguards and user confirmation.

**Approach:** Implement `row_interpret` LLM request building and interpretation in `packages/app/src/imports/set-aside.ts` and `row-interpret-request.ts` with strict AD-6 privacy gates (local by default, cloud only with `cloud_rows` opt-in, never for private accounts), persist proposals in `import_row.proposal`, render proposals beside raw lines in Needs review, and commit confirmed proposals through the original batch.

## Boundaries & Constraints

**Always:**
- `row_interpret` runs only on a local provider unless the provider has an explicit `cloud_rows` opt-in (`cloudRows === true`).
- A non-local / cloud provider is NEVER sent set-aside rows from private accounts (`account.isPrivate === true`); attempts throw `AppError("PermissionDenied", "Cannot send private account rows to a cloud LLM provider")`.
- If a cloud provider is assigned to `row_interpret` without `cloudRows: true`, row interpretation throws `AppError("PermissionDenied", "Cloud provider not permitted for row interpretation without cloud_rows opt-in")`.
- Output is strictly a schema-validated transaction proposal (`postedOn`, `amountCents`, `description`, optional `confidence` and `explanation`); nothing is committed to the ledger until explicitly confirmed by the user.
- Confirmation commits the transaction to the ledger through the original import batch via `fixSetAsideRow`, updates `import_row.status = "committed"`, clears `reason`, increments `batch.new_count`, resolves `import.set_aside` when all rows reach terminal status, and syncs closing balance.
- Live request preview in Settings for `purpose: "row_interpret"` uses the real request builder (`buildRowInterpretRequest`) per AD-6.
- Database migration `0023_import_row_proposal.sql` adds nullable `proposal` column to `import_row`.

**Never:**
- Never commit ledger transactions automatically during interpretation without explicit user confirmation.
- Never leak private account names, person identities, or private rows to external cloud LLM providers.
- Never implement loan rate-change proposals in this story (deferred to epic-loans-property per 2026-10-26 decision).

## Design Notes

- **AD-6 Privacy Sanitiser for Row Interpretation:** Unlike `categorise` which receives already structured transaction fields, `row_interpret` operates on raw statement rows. It is local by default. If a cloud provider is assigned, it requires `cloud_rows: true` and strictly forbids any row from an account where `isPrivate === true`.
- **Proposal Storage on `import_row`:** Adding `proposal: text` to `import_row` maintains data locality with the staged row, supports auditing, and survives server restarts without creating a secondary proposal table.
- **Confirmation Semantics:** Confirmation directly invokes the existing ledger commit pipeline in `fixSetAsideRow`, ensuring fingerprinting, deduplication, rule classification, transfer matching, and closing balance updates occur identically to manual edits.

# Ticket Implementation Plan
{ status: in-progress, all inline }

## Summary

Give the payee a web **domain**, fetched lazily and privately — never by the browser.

Today `payee.website_url` exists in the schema but nothing reads or writes it, so the UI has no merchant identity beyond a name. This ticket establishes the domain on the payee row, then fetches that merchant's favicon **from the server** under the AD-8 privacy guard (only for shared/public payees — `scope_person_id IS NULL`), stores it as an encrypted attachment (AD-21), and serves it to the viewer's browser through an app-owned route so the CSP can stay `img-src 'self'`.

Three seams are involved, all following patterns the codebase already has:

1. **Domain** — `PayeeDomain` is owned by `classify` (`packages/app/src/classify/`). A pure `normaliseDomain()` there converts a URL or bare text into a lowercase registrable domain. It is filled in where a domain becomes *confirmed*: accepting a categorisation suggestion links the suggestion's domain to the payee; a later manual `websiteUrl` edit is kept as-is. (Import-confirmed domains already land via review-acceptance — `confirm` sets the payee through the review-accept path with `source: 'import'`.)
2. **Fetch** — a `logo-fetch` job kind (net lane, `retry: { maxAttempts: 1 }`) run by the server worker: an **AD-8 guard** (`payeeNeedsLogoFetch`) decides whether the payee still needs a logo — checked before any I/O and re-checked inside the recording write — and a handler in `apps/server/src/jobs/logo-fetch.ts` performs one plain `GET https://<domain>/favicon.ico` through an **injectable fetcher** (no redirect following — a 3xx fails closed), with a 256 KiB cap, an image mime allowlist (no SVG), and an `isBlockedAddress` check against the host's DNS answers before the request. Optional proxy support (`PANGOLIN_EGRESS_PROXY_URL` via an undici `ProxyAgent`) lets operators pin egress at the process level as well as with nftables (AD-8 names both).
3. **Serve** — `GET /api/payees/:id/logo` reads the attachment as the viewer, decrypts, and returns the image bytes like every other `/api` response (so `Cache-Control: no-store` applies, as elsewhere). The browser only ever loads `/api/...` URLs.

**Privacy is the spine of this ticket.** `canFetchMerchantLogo(payee)` is a pure predicate that refuses whenever `scopePersonId != null`, and it runs **before** any network call. The test asserts an outbound fetch mock has zero calls for a private payee — this is the privacy guarantee, tested. The enqueue is in the same transaction as the action that confirms the domain, so a refused transaction enqueues nothing.

No DB migration is needed (`Payee.websiteUrl` and the `attachment` table exist), and no payee is created, renamed, or merged — that is the next ticket (5.10).

- **`Payee.websiteUrl`** (VARCHAR(2000), nullable) exists in `packages/db/src/schema.ts` — no migration; the column is currently dead.
- **`domain` is derived, not stored**: it is held in `Payee.websiteUrl` normalised to a lowercase host. A derived value is stored where it can be null and recomputed — consistent with `attachment.content_text` precedent.
- **Logo state is `payee.logoAttachmentId`** (column exists at baseline — no migration): `null` = no logo yet, an id = stored. `payeeNeedsLogoFetch(payee)` = `scopePersonId === null && websiteUrl !== null && logoAttachmentId === null`. A failed fetch leaves it null but the once-ever rule holds via the job ledger (a completed job is not re-enqueued; `payeeNeedsLogoFetch` is re-checked in the write so a payee that gained a logo meanwhile links nothing).
- **`SuggestionRow.websiteDomain`** exists at baseline and the categorise engine records it — "domain confirmed" means an *accepted* suggestion carrying a `websiteDomain`, and the engine already writes the domain onto suggestions.
- **`setSplitField` already carries the exact seam**: inside its own write transaction it closes the open suggestion (`resolveOpen`, lines ~209–224, with `outcome` + `websiteDomain` in hand) and then runs `registerSplitFieldListener` listeners **in the same transaction** (line ~225). The hook's own comment — "The hook for closing open suggestions (AD-10) once `classify` has them… There are none yet" — sanctions this ticket as its first consumer. The current listener signature `(tx, audit, event)` lacks `ctx`, and the event lacks the closed suggestion; both are additive extensions (no existing callers break).
- **Attachment is `system`-owned** (AD-10) and already encrypted-at-rest: reuse the existing `putEncrypted()` helper in `packages/app/src/system/attachments.ts` to write, and read it back through `getEncrypted()`. AD-8 is satisfied by the guard, not by storage.
- **Job wiring (as built, KEEP)** — `logoJobs(deps)` in `apps/server/src/jobs/logo-fetch.ts` joins `createJobs` in `apps/server/src/jobs/index.ts` beside backup/closing-balance jobs; `server.ts` passes `logosEnabled` (`PANGOLIN_LOGOS_ENABLED`) and `egressProxyUrl` (`PANGOLIN_EGRESS_PROXY_URL`) from config.
- **Review-acceptance seam (loop-1 fix)** — `acceptSuggestionItem()` (baseline shape, `void`) runs the domain link + enqueue **inside the acceptance transaction** via the split-field listener below — no second `write()`.
- **Fetch guardrails (as built, KEEP)** — one `GET https://<domain>/favicon.ico`, `redirect: "manual"` and **fail closed on any 3xx** (the frozen row demands *one request*, not redirect chasing); 256 KiB cap by header and streamed read; mime allowlist without SVG; 404 completes quietly (no logo, no failure). `retry: { maxAttempts: 1 }` on the job kind: a failed attempt goes straight to `dead` — **never retried automatically**, the frozen once-ever row's exact mechanism.
- **Internal addresses (`isBlockedAddress`)** — before any request, the fetcher resolves the host (`dns.promises.lookup`, injectable for tests) and refuses when **any** answer is loopback (127/8, ::1), RFC1918 (10/8, 172.16/12, 192.168/16), link-local (169.254/16, fe80::/10), unique-local (fc00::/7) or an unspecified/metadata address. `normaliseDomain` already refuses to *store* IP literals/localhost/reserved names, so the two guards meet every case of the frozen row. The resolve→connect window (DNS rebinding) stays nftables' belt (AD-8: "application-level guard is primary, network policy is belt-and-braces") — recorded limitation.
- **HTTP serving** — `GET /api/payees/:id/logo` reads through the viewer's uow and returns bytes with `reply.type()` + `Buffer` (like `imports-upload.ts`); CSP is set unchanged by `apps/server/src/http/app.ts` (AD-24).
- **UI**: `BarListsCard` is `variant: 'bar' | 'donut'` (merchant tab is the donut); `LatestTransactionsCard` and `TransactionsTable` rows carry merchant cells. `packages/web/vite.config.ts` sets no CSP — Fastify sets the header (AD-24), so no test asserts on vite config.

## Bonded Constraints

- **Privacy guard before fetch** — `payeeNeedsLogoFetch()` must run before any network I/O; a private payee performs zero outbound requests. [→ Enforce-by-example: "`canFetchMerchantLogo(payee)` returns false for a private payee; fetcher refuses and records nothing"]
- **Enqueue inside the business transaction** — the logo enqueue rides the same uow/transaction as the action that confirms the domain (acceptance, `websiteUrl` write, import confirm) — a refused write enqueues nothing. [→ Enforce-by-example: "Enqueue on acceptance or when a public payee newly sets `websiteUrl`"]
- **CSP stays `img-src 'self'`** — no change to `apps/server/src/http/app.ts`; every logo URL is `/api/...`. [→ Enforce-by-example: "Browser never calls a third-party origin"]
- **Once-ever** — the guard reads `payee.logoAttachmentId` before fetch; `failed` is never retried automatically (`retry: { maxAttempts: 1 }` → dead on first failed attempt). [→ Enforce-by-example: "Fetch once-ever per payee"]
- **Internal addresses never requested** — `isBlockedAddress()` over the host's DNS answers before the request, plus `normaliseDomain` refusing IPs/localhost/reserved names at store time. [→ Enforce-by-example: "A domain that resolves to an internal address is never requested"]
- **AD-21 at rest** — the logo bytes are written with `putEncrypted()`.
- **No migration** — uses existing `Payee.websiteUrl`, `Payee.logoAttachmentId`, `SuggestionRow.websiteDomain`, `attachment`, and `job` tables.
- **No payee creation/renaming/merging** — that is ticket 5.10.
- **AD-10 ownership** — payee rows (domain link, `logoState`) are written only by `classify` functions; `system` never writes a payee row directly.
- **AD-1 layering** — the job handler holds no business rule: get-or-create, guard, delegate, record through `classify`.
